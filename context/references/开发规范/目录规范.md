
# 单体应用开发规范
本项目后台用python来写

## 1. 规范目标

为了统一单体应用的开发、部署、启动、停止、数据库初始化、数据库升级以及日志管理方式，所有单体应用应遵循统一的目录结构、脚本规范和运行规范。

本规范主要解决以下问题：

1. 应用如何统一启动。
2. 应用如何统一停止。
3. 数据库、数据库用户及密码如何统一创建。
4. 数据库表结构如何初始化。
5. 初始化数据如何安全、重复执行。
6. 数据库表结构如何进行版本化修改。
7. 数据库修改脚本如何保证重复执行不会产生错误。
8. 应用日志如何统一记录。
9. 应用日志存放在哪里，以及如何进行日志轮转。
10. 新应用部署到一台新的服务器后，可以通过标准脚本完成部署和运行。

# 3. 统一的启动脚本

每个单体应用必须提供：

```text
scripts/start.sh
```

启动脚本是应用启动的**唯一标准入口**。

开发人员、运维人员以及部署系统不得直接执行：

```bash
python app/main.py
```

或者：

```bash
uvicorn app.main:app
```

生产环境必须统一通过：

```bash
./scripts/start.sh
```

启动。

## 3.1 启动脚本职责

`start.sh` 至少需要完成以下工作：

```text
检查运行环境
    ↓
检查配置文件
    ↓
检查数据库连接
    ↓
检查是否已经运行
    ↓
创建必要目录
    ↓
执行数据库初始化/升级
    ↓
启动应用
    ↓
记录 PID
    ↓
输出启动结果
```

例如：

```bash
#!/bin/bash

set -e

APP_HOME="/opt/my-service"
APP_NAME="my-service"
PID_FILE="$APP_HOME/run/$APP_NAME.pid"

cd "$APP_HOME"

# 检查是否已经运行
if [ -f "$PID_FILE" ]; then
    PID=$(cat "$PID_FILE")

    if kill -0 "$PID" 2>/dev/null; then
        echo "$APP_NAME is already running, pid=$PID"
        exit 0
    fi

    rm -f "$PID_FILE"
fi

# 创建运行目录
mkdir -p "$APP_HOME/run"

# 启动应用
nohup python -m app.main \
    >> /var/service/log/$APP_NAME/application.log 2>&1 &

PID=$!

echo "$PID" > "$PID_FILE"

echo "$APP_NAME started, pid=$PID"
```

## 3.2 启动脚本要求

启动脚本必须满足：

* 可以重复执行。
* 应用已经启动时不能重复启动。
* 启动失败必须返回非 0。
* 启动成功必须返回 0。
* 必须记录 PID。
* 必须使用绝对路径。
* 不依赖当前 Shell 的工作目录。
* 不依赖用户手工设置环境变量。
* 不允许将密码直接写在脚本中。

例如：

```bash
./scripts/start.sh
```

重复执行：

```bash
./scripts/start.sh
```

应该得到类似：

```text
my-service is already running, pid=12345
```

而不是启动第二个实例。

# 4. 统一的停止脚本

每个单体应用必须提供：

```text
scripts/stop.sh
```

停止应用必须统一使用：

```bash
./scripts/stop.sh
```

## 4.1 停止流程

推荐：

```text
读取 PID
   ↓
检查进程是否存在
   ↓
发送 SIGTERM
   ↓
等待应用正常退出
   ↓
超时
   ↓
发送 SIGKILL
```

例如：

```bash
#!/bin/bash

APP_HOME="/opt/my-service"
APP_NAME="my-service"
PID_FILE="$APP_HOME/run/$APP_NAME.pid"

if [ ! -f "$PID_FILE" ]; then
    echo "$APP_NAME is not running"
    exit 0
fi

PID=$(cat "$PID_FILE")

if ! kill -0 "$PID" 2>/dev/null; then
    rm -f "$PID_FILE"
    echo "$APP_NAME is not running"
    exit 0
fi

echo "Stopping $APP_NAME, pid=$PID"

kill -TERM "$PID"

for i in {1..30}; do
    if ! kill -0 "$PID" 2>/dev/null; then
        rm -f "$PID_FILE"
        echo "$APP_NAME stopped"
        exit 0
    fi

    sleep 1
done

echo "Force killing $APP_NAME"

kill -KILL "$PID"

rm -f "$PID_FILE"

echo "$APP_NAME stopped"
```

## 4.2 为什么优先使用 SIGTERM

不能直接：

```bash
kill -9
```

因为应用收到 `SIGTERM` 后，可以进行：

* 数据库连接关闭
* 文件关闭
* 消息消费停止
* HTTP 请求处理完成
* 临时资源清理
* 临时文件清理

因此标准停止流程应该是：

```text
SIGTERM
   ↓
等待
   ↓
正常退出

如果长时间不退出
   ↓
SIGKILL
```

# 20. 统一的 status.sh

虽然你的原始大纲没有这一项，但实际工程中强烈建议增加：

```text
scripts/status.sh
```

用于检查：

```bash
./scripts/status.sh
```

输出：

```text
Service: my-service
Status: RUNNING
PID: 12345
Port: 8080
Uptime: 2 days
Database: OK
```

这样：

```text
start.sh
stop.sh
status.sh
```

就形成完整的应用生命周期管理。

# 21. 统一的 restart.sh

```text
scripts/restart.sh
```

实现：

```text
stop.sh
   ↓
start.sh
```

例如：

```bash
#!/bin/bash

set -e

SCRIPT_DIR="$(cd "$(dirname "$0")" && pwd)"

"$SCRIPT_DIR/stop.sh"
"$SCRIPT_DIR/start.sh"
```

这样部署时：

```bash
./scripts/restart.sh
```

即可。
