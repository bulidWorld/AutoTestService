# 阶段一数据库结构

表定义的唯一来源是 [010_project_interfaces.xml](010_project_interfaces.xml)，格式遵循开发规范的 `database.xsd`，由 `scripts/sync_schema.py` 生成并同步 PostgreSQL 表结构。表变更继续写 XML，不维护另一份手写建表 SQL。

## 表与关系

| 表 | 主键 | 保存的数据 |
| --- | --- | --- |
| `projects` | `id`，自增 integer | 项目名称、描述、创建和更新时间 |
| `yaml_files` | `id`，自增 integer | 所属项目、逻辑文件名、当前版本号及时间 |
| `yaml_versions` | `(file_id, version)` | 文件名、导入时间、接口数量、OpenAPI 信息、原始 YAML 和完整解析文档 |
| `api_interfaces` | `id`，自增 integer | 所属文件及版本、方法、路径、摘要、参数、请求体、响应、认证与 servers 定义 |

项目 → 文件 → 版本 → 接口保留逻辑关联字段，但数据库不设置外键。程序负责校验项目、文件及版本是否存在、归属是否正确，以及当前版本是否有效。删除父记录不会自动删除子记录，关联清理必须由程序显式执行。

项目、文件及接口主键使用 `integer GENERATED BY DEFAULT AS IDENTITY`，由数据库生成；`project_id` 和 `file_id` 关联字段同为 integer。YAML 契约使用 `integer / int32`，合法 ID 范围为 1～2147483647。自增序列在事务回滚后不会回退，因此 ID 可能有间断，不应要求连续。时间使用 `timestamptz`。结构化接口定义使用 JSONB，接口详情读取前由业务层脱敏；数据库保存的原始 YAML 与解析文档不能直接返回给客户端。

## 约束

- 项目名称系统内唯一，文件名称项目内唯一，采用区分大小写比较；名称不允许为空或带首尾普通空格。业务层还需要按接口契约完成完整空白字符归一化。
- 同一文件、同一版本内，HTTP 方法加路径唯一；不同版本可保留相同方法和路径，但接口 ID 不复用。
- 版本号及接口数量必须为正数，OpenAPI 版本为 3.0.x，文件名后缀为 `.yaml` 或 `.yml`，不包含目录路径。
- 原始 YAML 为非空文本，UTF-8 字节数不超过 5 MiB。
- 参数、servers 为 JSON 数组，请求体为 JSON 对象或 SQL NULL，响应和认证定义为 JSON 对象；响应映射不得为空。
- 更新触发器禁止直接修改 `yaml_versions` 或 `api_interfaces`。全量更新必须新增版本及接口记录，再切换文件的当前版本。
- 项目和文件列表、按版本排序的接口列表有对应索引。接口计数及版本的 `is_current` 由查询关联得出；项目和文件不重复存储接口计数。

数据库不替代导入校验：UTF-8、OpenAPI 语义、Schema 支持范围、引用解析、实际接口数量与 `interface_count` 一致性均由后续导入服务负责。数据库也不承担页面二次确认及未来任务引用/运行状态的业务校验。

## 导入与更新的事务要求

数据库不校验跨表关联。导入服务必须在事务中校验项目/文件归属并保证当前版本存在；需要通过行锁协调更新和删除，防止并发操作留下孤立数据。版本不可变触发器和函数继续由 XML 定义。

首次导入必须在一个事务中完成：创建 `yaml_files`（当前版本 1）→ 创建版本 1 → 插入接口集合 → 提交。程序必须保证文件、版本和接口集合完整后才提交，否则主动回滚。

全量更新必须锁定对应文件行（`SELECT ... FOR UPDATE`），读取当前版本号，新增下一版本及接口集合，再更新 `current_version` 和 `updated_at`，最后提交。失败时回滚全部操作。并发更新由文件行锁串行化，不复用版本号。

历史版本没有单独修改或删除接口。删除文件时，程序在同一事务内依次删除接口、版本、文件；删除项目时，还需删除全部所属文件并最后删除项目。程序同时负责二次确认及未来的任务引用/运行状态检查。

## 执行同步与验证

在项目根目录执行：

```bash
# 预览待执行 SQL，不修改数据库
bash scripts/db_sync.sh --dry-run --sql-out /tmp/auto-test-service-schema.sql

# 实际初始化或升级
bash scripts/db_sync.sh

# 再执行应显示 pending: 0
bash scripts/db_sync.sh

# 启用真实数据库约束测试，测试插入的数据全部回滚
AUTOTEST_DB_TESTS=1 .venv/bin/python -m pytest tests/test_phase1_database.py -q
```

需要自定义连接时，在上述命令前设置 `APP_CONFIG` 为实际配置路径。运行数据库测试前应先同步表结构；日常 `pytest` 默认跳过需要数据库的测试。

同步器另有 `schema_xml_migration` 和 `database_change_log` 两张元数据表，分别记录 SQL 校验和及变更审计。重复执行不会重放未变化的 DDL；修改已存在列类型、唯一约束或索引时，需在新 XML statement 中添加独立、幂等的升级 SQL，不应只修改原 CREATE TABLE 定义。

## 移除已有外键

[030_remove_foreign_keys.xml](030_remove_foreign_keys.xml) 通过 PostgreSQL 系统目录查找四张业务表的外键并执行 DROP CONSTRAINT。运行 `bash scripts/db_sync.sh` 即可升级已有数据库；重复执行安全。新建库从表定义开始就不创建外键。

主键、唯一约束、CHECK 约束、索引和历史定义不可变触发器继续提供各自的校验。删除迁移文件不会恢复已经移除的外键。

## 项目级多任务组

[040_task_collections.xml](040_task_collections.xml) 定义任务组配置、成员批次、组运行、
成员运行关联和参数覆盖审计五张表。接口见
[rest-task-collection.yaml](../docs/%20rest-api/rest-task-collection.yaml)，执行与事务规则见
[设计说明](../context/requirement/2-2.support_task_group/design.md)。

- 成员任务属于同一项目；同组任务不重复，position 为正整数，可重复且不要求连续。
- 按 position 升序执行批次，同批并发。批次输入保存于成员 input_parameters，ready 表示输入已冻结、允许调度。
- 每个成员复用 task_runs 保存独立运行结果。活动组预约全部成员，即使某个成员已完成也不能再次独立启动。
- 批次全部成功后按 task_id 升序合并参数；任何成员失败，本批不提交共享参数，后续成员跳过。
- 覆盖记录保存原、新任务及运行 ID，logged_at 作为 ERROR 日志投递状态，不保存参数值。
- 单独删除组保留运行历史；删除任务前必须先解除组配置引用。项目删除显式清理全部关联历史。
- 原任务内步骤组功能已移除；已有数据库中的旧表和可空列不再使用，不自动删除历史结构。

部署前执行 `bash scripts/db_sync.sh`；XML 内包含运行期新增字段的幂等升级语句。

## 统一任务执行节点

[020_task_compose.xml](020_task_compose.xml) 保存最终任务表结构，
[050_task_execution_nodes.xml](050_task_execution_nodes.xml) 保存幂等结构升级。
当前同步入口读取 `database.schema_directory`（默认 `db`）下全部 `*.xml`，无需增加文件白名单。

- `task_steps` 使用 `step_type`、`execution_scope`、`parent_step_id` 表示执行树；`position` 为兄弟排序值。
  REST 保存独立 `headers`、可选 `raw_body`；wait/parallel 不绑定接口，对应接口字段允许 NULL。
- `task_run_steps` 保存节点类型、范围及运行父引用；parallel 父节点的 `parallel_stats` 仅保存累计统计。
  并发 REST 不写 `task_requests`，不保存逐请求响应或响应耗时；普通和清理 REST 继续关联叶子运行步骤。
- `task_runs` 增加 `execution_stage`、主流程错误字段及 `cleanup_status`，清理结束前保持 running。
  `task_run_parameters.published` 默认 false，明确区分成功提取与上下文发布。
- 配置和运行节点均有 `(task/run_id, execution_scope, parent_id, position, id)` 索引。
  新增字段关系和取值由业务事务校验，不增加外键或 CHECK。

结构升级不转换旧 headers 绑定、任务配置或历史快照。REST/wait/parallel 专用字段组合、
父子映射、依赖和执行调度由业务事务与执行器处理；部署时同步数据库并重启应用加载新执行逻辑。

可在独立测试数据库验证新建结构与重复升级：

```bash
AUTOTEST_DB_TESTS=1 .venv/bin/python -m pytest tests/test_execution_node_database.py -q
```

测试创建临时 schema 并在结束时回滚，不修改已有业务表。

## G1～G6 执行策略扩展

`050_task_execution_nodes.xml` 增加 `task_steps.options jsonb`，保存鉴权、条件、参数更新、动态等待及原始路径/查询策略；`wait_milliseconds` 扩展为 bigint，单次等待最多 30 天。状态字段增加业务终态 blocked，并发统计增加 blocked_count；不使用 PostgreSQL enum。运行参数赋值允许 JSON null，不受断言结果影响。部署时使用现有同步流程；本轮未执行迁移或测试。

compute 参数使用 source_type=expression 及 task_parameters.expression_source JSONB，表达式位于 task_steps.options.expressions，默认时区为 Asia/Shanghai。首次创建与已有数据库迁移均已补定义；本轮未执行迁移或测试。
